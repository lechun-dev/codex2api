## 范围与边界

依据只读排查报告，第一批修复管理页查询和 Grok 维护队列。
代码基线为本地 main 的 61b9708b；报告中部署目录标记的版本为 7897c8e，

## 1. API Key 最近使用时间

- 仅 MySQL 改用固定 Key 参数的独立子查询，每批最多 32 个 Key，
  使用 UNION ALL 合并往返，避免关联子查询 ORDER BY 的 filesort。
- 复用现有 (api_key_id, created_at) 索引，不要求新索引或 FORCE INDEX。
- 仅包含仍存在的正数 Key ID；保留 status_code <> 499，不缩窄为成功请求。
- 时间仍取 created_at 最大值，不能假定更大的日志 ID 一定时间更晚。
- SQLite/PostgreSQL 查询不变。

本地隔离 MySQL 8.4.0，64 个 Key、262144 条模拟日志，包含最新端连续 499。
同一数据集、同一进程交替执行原查询和新查询，并核对每个 Key 的时间完全一致：

| 轮次（第一次运行） | 原关联查询 | 固定 Key 分批查询 |
|---|---:|---:|
| 首轮，包含预热影响 | 334.77 ms | 9.41 ms |
| 热缓存 1 | 29.81 ms | 8.04 ms |
| 热缓存 2 | 29.75 ms | 7.07 ms |

另一次与 Go 全量/竞态检查同时运行，热缓存结果为 92.07→31.39 ms、
57.66→9.99 ms，说明共享主机负载会影响数值，不能将上述倍数外推到生产。
未声称生产原来的 12.5 秒慢样本已经缩短到本地毫秒水平。

手工核对单个 Key 的只读 SQL（替换绑定参数；先在测试/受限环境验证）：

~~~sql
SELECT MAX(created_at) AS expected_last_used_at
FROM usage_logs
WHERE api_key_id = ? AND status_code <> 499;

EXPLAIN
SELECT created_at
FROM usage_logs
WHERE api_key_id = ? AND status_code <> 499
ORDER BY created_at DESC
LIMIT 1;
~~~

性能对比测试仅在显式设置 CODEX2API_MYSQL_PERF_TEST=1 时执行，
还需设置 CODEX2API_MYSQL_TEST_DSN 指向隔离实例。
测试创建并删除自己的临时数据库，禁止使用生产 DSN。

## 2. 管理页展示缓存

使用 Handler 内的有界内存缓存，不新增 Redis 数据结构或依赖：

- 30 秒新鲜期；过期立即返回旧值并合并后台刷新。
- 最多保留 5 分钟旧数据；更旧的数据不可继续当作可用结果返回。
- 每个 Key 同时只有一个加载，失败退避 5 秒，最多 64 个缓存条目。
- 加载有独立超时，一个浏览器取消请求不取消其他等待者共用的刷新。
- API Key 最近使用时间冷加载最多 2 秒；账号窗口最多 8 秒，
  今日用量/模型各最多 4 秒，页面请求保留原来的总超时。
- 缓存仅覆盖最近使用时间、账号 5h/7d 窗口、今日用量和模型统计。
  官方账单同步状态不缓存，避免回补完成后仍不断重试或显示旧状态。
- 账号页按规范化 ID 集合、当天零点、账号变更代数及运行时凭据代次分键。
  清空日志时清空展示缓存，在途旧刷新不能写回新缓存。
- 查询口径不变；失败不写入假零值。响应附带数据时间和 ready/stale/partial
  或 unavailable 状态，前端旧版本仍可读取原有字段。
- 不用于 API Key 鉴权、费用扣减、额度校验或调度决策。

本地 SQLite、4096 条模拟日志的真实 page-stats handler 基准（不含网络），
三轮各 200ms；两条路径都保留官方账单/账期相关查询：

| 场景 | 三轮耗时 / 次 |
|---|---|
| 每次清空展示缓存 | 9.501 / 9.484 / 9.524 ms |
| 命中展示缓存 | 0.0297 / 0.0315 / 0.0301 ms |

此项证明重复请求可以避免重新聚合，不代表生产冷请求或整页加载达到该耗时。
可使用 BenchmarkAccountPageStatsDisplayCache 重复测量。

冷查询仍会扫描明细；缓存不能代替账号专用预聚合。
现有 usage_log_hourly 不含 account_id/credential_generation，不能直接替换账号统计。

## 3. 维护队列

- 到期索引只做非锁定候选发现，每次最多 32 个候选。
- 在短事务中按主键顺序逐条 FOR UPDATE，并重新检查到期和租约。
  领取不再持有到期二级索引的范围锁。
- 仅对明确的 MySQL 1213 死锁牺牲者重试，最多 3 次重试，
  指数退避加随机抖动并尊重 context。
- 不重试 1205、断连、未知提交结果，不重放用户 AI 请求。
- 每次事务重试重新发现候选并清空结果；仅返回最终提交成功的任务。
- 完成/失败写回也做同范围的有界 1213 重试。
- 运行中的 Grok 队列每批生成独立租约 owner；完成和失败使用任务携带的 owner，
  避免同一个进程的旧租约写回新领取任务。
- PostgreSQL/SQLite 的领取分支不变，不依赖 MySQL 8 的 SKIP LOCKED。
